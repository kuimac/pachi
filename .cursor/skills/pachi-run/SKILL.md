# pachi-run

店舗の台データをブラウザで集め、判断 MD を書き、Pages まで公開する。

## いつ使うか

- 「〇〇での明日の動き方」「〇〇での午後の動き方」「〇〇での期待値が高い台」
- 閉店後の翌朝戦略、昼の午後戦略、任意の収集・分析・公開

## 手順

### 読むもの（これ以外を開かない）

`店舗一覧.md` 全文、`攻略情報/` の通読、台フォルダの CSV、`docs/`、画像は読まない。検索もしない。

```bash
python3 tools/brief.py store <店名または別名>
python3 tools/brief.py units <正規店名> --day YYYY-MM-DD
```

時間次（1時間おき）は `units` を出さない。

```bash
python3 tools/brief.py diff <正規店名> --day YYYY-MM-DD --save
```

差分に出た台だけ、狙い順の行を直す。`台分析.md` の全表はフル再分析のときだけ書き直す。攻略MDを開くのは `units` の「攻略なし」に出た機種だけ。

数値の列は `台分析.md` だけ。朝イチ・午後・期待値・重要ポイントは `順 | 台番号 | 機種 | やること | やめ時` と、台分析へのリンク。推定/実測の定義文は各MDに繰り返さない。

### 0. 公開リポジトリの取り扱い

- このリポジトリと GitHub Pages は **公開前提**。
- **公開してよい:** `プレイ履歴.md` の実プレイ明細、分析 MD の個人収支（`朝の結果` など）、Pages のプレイ結果。
- **置かない:** 本名以外に紐づく連絡先、ローカル絶対パス（`/Users/...`）、Cookie、`.env`、有料サイトの認証情報。
- スマホ取得用の GitHub Actions は無料公開データだけ。有料ログインは扱わない。


### 1. 店とモードを決める

1. `python3 tools/brief.py store <店名>` で正規店名・分析URL・リセット有無を取る。店舗一覧の全文は開かない。
2. 指示の店名は brief が正規店名へ解決する。
3. モードを決める:

| 指示の例 | モード | 主データ | 出力 MD（`YYYY-MM-DD/正規店名/`） |
| --- | --- | --- | --- |
| 明日の動き方 / 朝イチ / 閉店後 | morning | 前日までの集計 | `重要ポイント.md` `朝イチ狙い目.md` `台分析.md` |
| 午後の動き方 / 昼 | afternoon | 当日の出玉 | `午後狙い目.md`（必要なら `台分析.md` 更新） |
| 期待値が高い台 / 任意 | adhoc | 指示に応じた最新 | `期待値が高い台.md` など |

#### 朝イチ当日スケジュール（打ちながら）

朝から打つ日の既定。対象店の当日出玉を戦略へ載せる間隔。

| 枠 | 時刻・間隔 | やること | 出力 |
| --- | --- | --- | --- |
| 時間次更新 | **1時間おき** | 出玉を取得したあと `brief.py diff --save` の差分だけ反映 | 狙い順の行だけ直し publish。`台分析.md` は書き直さない |
| フル再分析 | **12:30**（Asia/Tokyo） | CSV 取り直し込みのフル再分析 | 上記＋`台分析.md` など当日戦略一式を更新して publish |
| 自分の実測 | 測ったチャンクごと | 250／1000玉の回転 | `実測回転.csv` 追記（250=信頼低、1000=信頼中） |
| 液晶・空席・右残し | 常時 | データより優先 | MD 必須ではない |

**12:30 フル再分析のスキップ条件**

- その営業日に、**12:30より前にユーザーがフル再分析の実行指示を出して実施済み**なら、予定の 12:30 フル再分析は **行わない**。
- 判定: 当日フォルダの判定 MD に `フル再分析: YYYY-MM-DD HH:MM（Asia/Tokyo）` があり、その時刻が当日かつ 12:30 未満。またはユーザーが「もうフルやった／スキップ」と明示。
- 時間次（1時間おき）の差分更新は、スキップ対象外。通常どおり続ける。
- フル再分析を実行したときは、該当 MD 見出し付近に必ず書く:

```text
フル再分析: 2026-11-09 11:40（Asia/Tokyo）
```

5〜10分おきの全台取り直しはしない（遅れ・混雑・打ちの邪魔）。島の大火・台切り・次候補探しでは、次の1時間枠を待たず時間次更新を前倒ししてよい。

日付フォルダは分析対象日（朝イチ判断ならその営業日）。未指定なら今日（Asia/Tokyo）。  
各 MD の見出し直後に、**分析を実行した時刻**を必ず書く:

```text
分析日時: 2026-11-07 23:10（Asia/Tokyo）
```

フォルダ名は日付のみ。時刻は本文の `分析日時` に載せる。

#### スナップショットと追っかけ

- 判断 MD（`重要ポイント` `朝イチ狙い目` `午後狙い目` `期待値が高い台` `台分析` `分析不可`）は、日付フォルダが記録になる。
- **追っかけ更新してよいのは当日（Asia/Tokyo）のフォルダだけ。** 時間次・フル再分析も同じファイルを上書きする。翌日以降の下書き（まだその日付が来ていないフォルダ）も、その日が来るまで上書きしてよい。
- **日付を過ぎたフォルダはスナップショット。** 書き換えない。確認は店舗ページの「過去の判断」からその日のページを開く。
- 店舗ページは「当日の判断」と「過去の判断」を分けて出す。当日欄は判断 MD へのリンク、過去欄は日付ごとのスナップショット。

### 2. 収集（ブラウザ）

1. 分析URLを開く。PC では Cursor IDE Browser または実 Chrome。ログインが要るサイトは PC セッション優先。
2. **4円パチンコ全台**だけ取る。
3. CSV を既存形式で `正規店名/<機種名>/<台番号>/` に保存（`スタート.csv` `大当り一覧.csv` `大当り履歴データ.csv` など）。列名は既存楽園町田店に合わせる。
   - **日付があるものはすべて新しいものが上（降順）**。`大当り履歴データ.csv`（日内も当り回数の大きい＝新しい方が上。最終スタート行 `回数=-` はその日の先頭）、`大当り一覧` など日次CSV、Pages の日付フォルダ一覧・日次インデックス・履歴表・台の日次表も同じ。棒グラフだけ左→右の時系列（右端＝当日）。
4. **現地の1000円実測**（「○回転」「250玉」など）が出たら、同じ台フォルダの `実測回転.csv` に追記する（下記）。
5. Cloud でログイン壁・CAPTCHA・サイト拒否が出たら迂回しない。失敗を報告し PC Remote 再実行を促して止める。

#### 実測回転.csv（必須フォーマット）

`正規店名/<機種名>/<台番号>/実測回転.csv`

```text
日時,玉数,回転数,回転/250玉,通常のみ,移転後,メモ
2026-11-08 13:44,250,19,19,yes,yes,島移動後の1回目
2026-11-08 14:10,1000,74,18.5,yes,yes,追加で1000玉
```

- `回転/250玉` = `回転数 × (250 ÷ 玉数)`（250玉なら回転数と同じ。比較用に常に /250 換算）
- 通常時のみ数えたとき `通常のみ=yes`。電サポ混入は `no` かメモに書く
- `移転後=yes` … 直近の島移動・台入れ替え・釘の入れ直しなどの**あと**で測った値。移転前の旧実測は信頼しない
- **玉数で信頼度が違う**: 250玉=信頼低、1000玉=信頼中、2000玉以上=信頼高。分析では数値だけでなく玉数を併記する
- **最新行が「実測/250玉」**。表示例: `19（250玉・信頼低・移転後）` / `18.5（1000玉・信頼中・移転後）`

#### 推定/250玉（取得データ・実測とは別）

大当り履歴の通常時区間から換算する（打ち出し100玉/分前提）。

- 連チャン（5分以内 or スタート≤40）を塊にする
- 塊と塊のあいだ: `スタート ÷ 経過分 × 2.5`
- 直近最大6区間の中央値。表示例: `19.1（推定・6区間）`
- 履歴が無い店・台は `—`（Pages の台ページでも同じ算出を出す）

#### スタートリセット

`brief.py store` の `日次集計リセット` / `台スタートリセット` を使う。リセット傾向の店では閉店スタートを翌朝の残スタートとして使わない（遊タイム残りも液晶確認）。

### 3. 分析

1. [`templates/`](../../../templates/) の該当テンプレを使い、判断 MD を書く。
2. `{{分析日時}}` を Asia/Tokyo の現在時刻（`YYYY-MM-DD HH:MM`）で埋める。
3. ボーダー・天井・遊タイムは `brief.py units` の機種行を使う。攻略MDを開くのは「攻略なし」の機種だけ。
   - **盤面ガイドは機種ごと**（共通の `board-guide.png` だけにしない）。新規機種は `tools/enrich_board_guides.py` で系列別の説明＋`攻略情報/images/boards/` の図を出すか、同等の詳細を手書きする。
4. **機種名と台番号を必ずセットで書く**（表・狙い順・重要ポイント・触らない欄も同様）。
   - 台番号は数字のまま（HTML 化でリンクされる）。
   - 「鬼がかりが良い」「電音部は見送り」だけにせず、対象台番号を列挙する。機種単位の総評を書く場合も、根拠にした台番号を残す。
5. **機種名 → 攻略情報リンクが必須**。
   - Pages ビルドが本文中の機種名を `攻略情報/` へ自動リンクする（短縮名も可能な範囲で解決）。
   - MD に手動で機種リンクを書くときは `攻略情報/<機種名>.md` を指す。台データや店舗ページだけにしない。
   - 攻略 MD が無い機種を出すときは、先に `攻略情報/` を追加するか、自動リンクが拾える表記（公式に近い機種名）で書く。
6. **`## 通常画面での打つ順番` を必須**（`朝イチ狙い目` / `午後狙い目` / `期待値が高い台` / `重要ポイント`）。
   - 右残し確認・天井／遊タイム線の拾いとは **別枠**。通常画面になった台だけを座る／測る順に並べる。
   - 表は最低でも `順 | 台番号 | 機種 | やること | やめ時`。各行に台番号＋機種名。
   - 遠隔で台番号が無い店は、到着後に番号を埋める前提で順の枠を先に書き、判明次第更新する（セクション自体は省略しない）。
   - 差玉上位の「結果台」は通常画面の測り順に入れない（右以外は触らない）。
7. **推定/250玉** と **実測/250玉** は `台分析.md` の表だけに書く。値は `brief.py units` の推定・実測列（無ければ `—`）。250玉実測だけで強判断しない。他のMDへ定義文や同じ数値列を繰り返さない。
8. **天井・遊タイムなしの台も必ず台分析に含める**（4円全台）。
   - 台分析の表から天井なし機種を省略しない。
   - 天井なしの主根拠は **推定/実測回転 vs ボーダー**。深さ・ハマりだけを理由に「対象外」と書かない（「深さでは座らない。回転次第」は可）。
   - 遊タイム付きは残り回転も併記。右打ち残しはどちらも液晶優先。
   - 朝イチ・午後・期待値の狙い順は、座る台だけ。天井なしでも回転根拠があれば順に入れる。

### 4. 公開（必須・人手を待たない）

```bash
./tools/publish.sh "Analyze <正規店名> <YYYY-MM-DD> <morning|afternoon|adhoc>"
```

- 中で `python3 tools/build_html.py` → 変更があれば commit → `git push origin HEAD`
- 変更なしなら空 commit しない
- push 失敗時は Pages 未反映と明示し、認証を案内して止める
- 完了報告に含める:
  - Pages: https://kuimac.github.io/pachi/
  - 店舗ページ: `https://kuimac.github.io/pachi/<YYYY-MM-DD>/<URLエンコード店舗名>/`

### 4.1 Pages の日付並び

日付がある UI はすべて **新しいものを上**（降順）。日付フォルダ一覧・日次インデックス・大当り履歴・台の日次表など。棒グラフだけ左→右の時系列（右端＝当日）。

### 4.2 全台一覧・出玉ランキング Pages（店舗下層）

`build_html.py` が、全台 CSV がある店だけ店舗ハブ下層へ最新ページを出す。`publish.sh` は先に `update_guide_installs.py` で攻略の **設置店舗**（取得日時付き）を更新する。

| ページ | 生成先 | ソース |
| --- | --- | --- |
| 全台一覧 | `docs/店舗/<店名>/全台一覧.html` | `全台データ_YYYY-MM-DD.csv`（店フォルダ優先） |
| 出玉ランキング | `docs/店舗/<店名>/出玉ランキング.html` | `出玉ランキング_YYYY-MM-DD.csv` |
| 天井・遊タイム機 | `docs/店舗/<店名>/index.html` の `#ceiling` | 最新 `全台データ_*.csv` ∩ 攻略の天井／遊タイム |

- **取得日時**は `tools/prefetch_snapshots/<店>/` の `fetched_at`、または当日の `生データ取得結果.md` の取得日時（Asia/Tokyo）。ファイル mtime は使わない。
- ランキングの **ホール集計期間**（snapshot の `period` / メモの集計期間）があれば併記。
- 店舗ハブ・日付店舗ページからリンク。日付フォルダ側にも同 CSV の HTML（取得時刻付き）が出る。
- CSV が無い店はページを作らない（リンクも出さない）。
- **天井・遊タイム機**は、最新全台取得で台がある機種だけ。攻略の天井／遊タイムが非搭載・なし・調査中の機種は載せない。機種名は攻略情報へリンク。該当機種が無い店はセクション自体を出さない。

#### 今後データを取得したら

1. いつもどおり CSV を置く（`prefetch_ranks.py` / `fetch_site777_all_units.py` / 手動）。中山UNO は加えて `fetch_dmm_ptown.py`（DMM/PSCUBE 併用。Site Seven を置き換えない。詳細は `docs/dmm-ptown-uno-fetch.md`）。
2. **必ず** `./tools/publish.sh "..."`（または `python3 tools/build_html.py` のあと push）。build 時に上記2ページと店舗ハブの天井・遊タイム機表が最新 CSV で上書きされる。
3. 取得だけして publish しないと Pages は古いまま。

### 5. Remote / Cloud / Actions（Mac 落ち時フォールバック）

Site Seven 無料枠は **住宅 IP（Mac）以外だと 403 になりやすい**。  
実測（2026-11-13）: Cloud VM・`ubuntu-latest` Actions とも `m.site777.jp` が **HTTP 403**。Mac からの取得のみ成功。  
DMM ぱちタウン（中山UNO jackpot）: **シェル＋ランキング画像は Cloud 200**。台番号別表の実体 P'sCUBE は **Cloudflare 403**（2026-11-14）。Mac で Site Seven と併用。

| 経路 | 取得（Site Seven） | DMM/PSCUBE（UNO） | 分析・Pages |
| --- | --- | --- | --- |
| Mac Cursor worker（優先） | 可 | 可（想定） | 可 |
| Mac keepalive / launchd（`tools/mac_keepalive_fetch.sh`） | 可（Mac 起床中） | UNO で `fetch_dmm_ptown`＋merge | `--publish` で可 |
| Mac self-hosted Actions（`Prefetch ranks (Mac self-hosted)`） | 可（runner 生存時） | 同上を Mac で | workflow 内で HTML 更新 |
| Cloud worker alone | **不可（403）** | シェル/画像のみ（PSCUBE 不可） | 既存 CSV があれば分析・publish のみ可 |
| ubuntu Actions（`Prefetch ranks (ubuntu probe)`） | **不可（監視用）** | 同上 | 失敗で `last.json` は潰さない |

1. スマホ・Remote では **まず Mac / PC Agent**（self-hosted worker）。
2. Mac worker が落ちていても Mac 本体が起きていれば:
   - `./tools/mac_keepalive_fetch.sh --store <店|all> --publish`  
     または launchd（`tools/macos/com.kuimac.pachi.fetch.plist`）
   - または GitHub Actions **`Prefetch ranks (Mac self-hosted)`**（要 self-hosted runner）
3. Mac がスリープ／オフラインで取得できないとき:
   - Cloud worker で **新規 Site Seven 取得はしない**（403・迂回禁止）。
   - 直近の成功 CSV（`出玉ランキング_*.csv` / `全台データ_*.csv`）があれば分析・`publish.sh` のみ実行。
   - データが無い／古いときは失敗を報告し、Mac 起床・keepalive・runner を促して止める。
4. **朝イチ**は prefetch の `mode=morning` 差分（成功スナップショット基準）で無料公開の変化を確認してから戦略 MD を書く（変更なしも明記）。
5. 有料・CAPTCHA・ログイン壁は Actions / Cloud でも取れない。迂回しない。
6. 公開完了の定義は **main への push 成功**。
7. 失敗スナップショットは `last_attempt.json` のみ。成功時だけ `last.json` を更新する（ubuntu 403 で朝イチ差分を壊さない）。

## やらないこと

- 4円以外の台の集計
- ログイン壁の回避・利用規約違反になりうる自動化
- 分析だけで push しないこと
- `.env` や秘密情報の commit
- ローカル絶対パス（`/Users/...`）・Cookie・認証情報の commit
